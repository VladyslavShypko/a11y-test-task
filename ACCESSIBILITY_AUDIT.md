# Accessibility audit

Audit basis: source and rendered interaction paths represented by this application. The fixes below preserve the supplied event, athletes, views, content, and mouse actions.

| Issue | User impact | WCAG 2.1 | Fix |
| --- | --- | --- | --- |
| Session filters were clickable `div` elements with a button role, but did not implement button keyboard activation. Only the first control was in the tab order. | Keyboard and assistive technology users could not reliably operate or discover the filter choices. | 2.1.1 Keyboard; 4.1.2 Name, Role, Value | Replaced them with native buttons; expose the selected choice with `aria-pressed` and keep every option keyboard reachable. |
| View choices were presented as tabs but lacked semantic roles, selection state, and relationships to their panels. | Keyboard and screen reader users could not reliably identify each view, its selected state, or its panel. | 2.1.1 Keyboard; 4.1.2 Name, Role, Value | Added `tablist`/`tab` roles, `aria-selected`, `aria-controls`, and panel labels. All tab buttons remain in the Tab sequence; native button activation works with Enter, Space, or click. |
| Result standing was represented by a dash while the row's background colour carried the distinction. | People who cannot distinguish the colours could not tell who qualified or was eliminated. | 1.4.1 Use of Color | Render the existing `Qualified`/`Eliminated` standing as visible text in each row. |
| Sort controls did not reliably expose their action or current direction to assistive technology. | Keyboard users need operable controls, and screen reader users need to know which column is sorted and in what direction. | 2.1.1 Keyboard; 2.4.6 Headings and Labels; 4.1.2 Name, Role, Value | Use named native buttons in the Rank and Bib headers, which support Enter and Space. Set `aria-sort` on the active column header to announce `ascending` or `descending`; leave it unset until sorting starts. Keep the SVG arrows decorative with `aria-hidden`, since `aria-sort` exposes direction to assistive technology. |
| The favorite star icon had no accessible name or state. | Screen reader users could not identify the action or whether the favorite was active. | 4.1.2 Name, Role, Value | Add a state-dependent accessible name and `aria-pressed`. |
| Expanded session details were not programmatically associated with their control. | Assistive technology users could not follow the Details button to its revealed content. | 1.3.1 Info and Relationships; 4.1.2 Name, Role, Value | Added a unique details ID, `aria-controls`, and an `aria-expanded` state on the Details button. |
| The alert preferences overlay lacked a modal name and modal state, and did not restore focus when closed. | Assistive technology users could not identify the dialog or that it was modal; keyboard users could lose their place after closing it. | 2.4.3 Focus Order; 4.1.2 Name, Role, Value | Associate the dialog with its heading, set `aria-modal="true"`, move initial focus inside, close on Escape, and return focus to the Manage alerts button after closing. |
| The event banner contains text but was marked decorative. | Screen reader users missed the course information embedded in the banner image. | 1.1.1 Non-text Content | Provide concise alternative text with the event and course facts shown in the graphic. |
